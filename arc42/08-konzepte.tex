\section{Querschnittliche Konzepte}

\subsection{Sicherheit}

Der Auth Service stellt nach erfolgreicher Anmeldung ein 60 Minuten gültiges
JWT aus. Die Validierung erfolgt zentral im API Gateway. Öffentliche
Endpunkte, beispielsweise Anmeldung, Registrierung und Produktabfragen,
können ohne Token aufgerufen werden.

Bei geschützten Aufrufen liest das Gateway die Benutzer-ID aus dem Token und
übergibt sie im Header \texttt{X-User-Id} an den zuständigen Service. Für
interne Aufrufe zwischen dem User Service und dem Auth Service wird zusätzlich
der Header \texttt{X-Internal-Key} verwendet.

\subsection{Kommunikation}

Die synchrone Kommunikation zwischen den Services erfolgt über REST. Für den
Versand von Bestellbestätigungen wird MQTT eingesetzt. Der Order Service
veröffentlicht dazu ein Ereignis mit QoS~1, das vom Email Service unabhängig
vom Kaufvorgang verarbeitet wird.

\subsection{Fehlerbehandlung}

Die Spring-basierten Services verwenden zentrale Exception Handler und ein
einheitliches Format für Fehlerantworten. Validierungsfehler werden mit
\texttt{400 Bad Request}, nicht gefundene Ressourcen mit
\texttt{404 Not Found} und Konflikte mit \texttt{409 Conflict} beantwortet.
Nicht behandelte Fehler führen zu \texttt{500 Internal Server Error}.

\subsection{Datenhaltung}

Jeder zustandsbehaftete Service besitzt eine eigene PostgreSQL-Datenbank.
Andere Services greifen nicht direkt auf diese Datenbank zu. Beziehungen
zwischen den fachlichen Bereichen werden daher über IDs statt über
datenbankübergreifende Fremdschlüssel abgebildet.
